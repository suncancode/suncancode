# Functional Testing, Random Testing and Fuzzing

---

## 1. What is Functional Testing?

**Functional testing** derives test cases directly from **program specifications** — not from the code itself.

- The word *"functional"* refers to the **source of information** used to design tests (the specification), NOT to what is being tested.
- Also known as:
  - **Specification-based testing** — tests are derived from specifications
  - **Black-box testing** — the tester has no view of the internal code

### What is a Functional Specification?
A **functional specification** is a description of the intended behavior of a program — it can be:
- **Formal**: mathematical notation, state machines, pre/post-conditions
- **Informal**: natural language requirements documents, user stories

---

## 2. Systematic vs Random Testing

### Random Testing (Uniform)
- Pick inputs **uniformly at random** from the input domain
- **Advantage**: Avoids designer bias — the test designer won't make the same logical assumptions as the programmer
- **Disadvantage**: Treats all inputs as equally valuable — does not focus on regions where bugs are likely to hide

### Systematic Testing (Non-Uniform)
- Deliberately select inputs that are **especially valuable**
- Usually by choosing **representatives of classes** that are likely to fail often, or not at all
- Focuses effort on parts of the input space where failures are dense

> **Functional testing is systematic testing** — it uses the specification to guide *which* inputs to choose.

---

## 3. Why Not Just Use Random Testing?

### The Needle-in-a-Haystack Problem

Consider a Java class `roots` that applies the quadratic equation:

```
ax² + bx + c = 0
```

**Bug**: The program does not correctly handle the case where `b² - 4ac = 0` AND `a = 0`.

- The failing inputs are only those where `a = 0.0` AND `b = 0.0`
- The input domain for a `double` is approximately `−2³¹ ... 2³¹ − 1`
- Probability of randomly picking `a = 0.0`: ≈ **1 / 2³²** ≈ 0.000000023%

**Failing values are sparse in the input space** — like needles in a very large haystack. Random sampling is astronomically unlikely to find them.

### Two Different Goals of Testing

| Goal | Approach |
|------|---------|
| **Estimate reliability** (proportion of bugs in input space) | Random sampling — needs unbiased statistics |
| **Find and remove bugs** | Systematic, non-uniform — focus on likely failure regions |

> For software testing, our goal is to **find and remove bugs** — not to estimate their density. So we use systematic, non-uniform approaches.

### The Haystack Analogy

```
Whole input space = haystack (enormous)
Bugs             = needles (sparse overall, but dense in certain regions)

Random testing:  picks hay at random → rarely finds needles
Functional testing: draws "pink lines" around regions likely to contain needles
                    → samples from each region → finds needles efficiently
```

## 4. Systematic Partition Testing

### Core Idea
**Partition** the input space into **classes** (regions) whose union covers the entire input space. Then draw at least one test case from each class.

```
Entire input space = Class₁ ∪ Class₂ ∪ ... ∪ Classₙ
```

- Failures are **sparse** in the whole input space...
- ...but **dense** in some parts (classes)
- By testing each class, we ensure we sample the dense (failure-prone) regions

### Why Partitioning Works
- Produces **fewer test cases** than random testing while achieving higher effectiveness
- Each class ideally contains inputs that behave **similarly** with respect to the program logic
- A fault that causes failures for one input in a class is likely to cause failures for other inputs in that class too

### Quasi-Partition (Practical Reality)
In practice, classes may **overlap** — so we call it a *quasi-partition*. This is acceptable because:
- We still cover all regions
- Overlapping tests provide redundancy, not harm

## 5. Equivalence Partitioning

**Equivalence partitioning** divides the input domain into **equivalence classes** — sets of inputs that are expected to be treated the same way by the program.

The goal: **one test case per class** is sufficient to represent the behavior of all inputs in that class.

### Key Principle
If the program handles `x = 5` correctly, it likely handles all valid inputs the same way. We don't need to test every valid value — just **one representative** per class.

### Example — Pizza Order System

**Specification**:
- Values **1 to 10**: valid order → show success message
- Values **11 to 99**: invalid → show error "Only 10 Pizza can be ordered"
- Values **≤ 0** or **≥ 100**: also invalid inputs

**Equivalence Classes**:

| Class | Range | Type | Representative |
|-------|-------|------|----------------|
| EC1 | 1 – 10 | Valid | 5 |
| EC2 | 11 – 99 | Invalid (too many) | 50 |
| EC3 | ≤ 0 | Invalid (too few) | -1 |
| EC4 | ≥ 100 | Invalid (out of range) | 150 |

**Test Cases** (one per class):

| Test | Input | Expected Output |
|------|-------|----------------|
| T1 | 5 | "Order successful" |
| T2 | 50 | "Only 10 Pizza can be ordered" |
| T3 | -1 | Error / invalid input |
| T4 | 150 | Error / invalid input |

## 6. Boundary Value Analysis

**Boundary value analysis (BVA)** complements equivalence partitioning by testing values **at the edges** of equivalence classes — because bugs are disproportionately likely to appear at boundaries.

### Why Boundaries?
Programmers commonly make **off-by-one errors**:
- `if (x < 10)` instead of `if (x <= 10)`
- `if (age >= 18)` instead of `if (age > 17)`

These errors only manifest at boundary values, not in the middle of a class.

### BVA Strategy: Test These Points
For each boundary between classes, test:
- The value **just below** the boundary
- The value **at** the boundary
- The value **just above** the boundary

### Example — Pizza Order (BVA applied)

Valid range: 1 to 10

| Boundary | Test Values | Reason |
|----------|------------|--------|
| Lower boundary (1) | 0, 1, 2 | Below, at, just above lower bound |
| Upper boundary (10) | 9, 10, 11 | Just below, at, just above upper bound |

**Full BVA test suite**:

| Test | Input | Expected Output |
|------|-------|----------------|
| T1 | 0 | Invalid |
| T2 | 1 | Valid — success |
| T3 | 2 | Valid — success |
| T4 | 9 | Valid — success |
| T5 | 10 | Valid — success |
| T6 | 11 | Invalid — "Only 10 Pizza" |

### Combined Example — Quadratic Equation `roots`

For `ax² + bx + c = 0`, the discriminant `D = b² - 4ac` determines the number of roots:

**Equivalence classes** (from the specification):

| Class | Condition | Roots |
|-------|-----------|-------|
| EC1 | D > 0 | 2 distinct real roots |
| EC2 | D = 0 | 1 repeated real root |
| EC3 | D < 0 | 0 real roots (complex) |
| EC4 | a = 0, b ≠ 0 | Linear equation — 1 root |
| EC5 | a = 0, b = 0, c ≠ 0 | No solution |
| EC6 | a = 0, b = 0, c = 0 | Infinite solutions |

**Boundary values**: D = 0 (boundary between EC1 and EC3) — this is exactly where the bug in `roots` lies!

## 7. Why Functional Testing? — Benefits

### 7.1 Timely
- Does not require completed code — only a specification
- Can begin **before coding starts**
- Useful for assessing testability and refining the spec early

### 7.2 Effective — Finds Missing Logic
- Functional testing is the best approach for **missing logic faults**
- A common problem: some program logic was simply **forgotten** during implementation
- Structural (code-based) testing **cannot find code that isn't there** — it can only test what exists

> Example: If a spec requires handling `a = 0` in the quadratic solver, but the programmer forgot to implement it, structural testing will never create a test for that case because the branch doesn't exist in the code.

### 7.3 Widely Applicable — All Granularity Levels

| Level | Specification Source |
|-------|---------------------|
| **Unit testing** | Module interface specification |
| **Integration testing** | API or subsystem specification |
| **System testing** | System requirements specification |
| **Regression testing** | System requirements + bug history |

Compare with structural testing, which only applies at **unit** and **integration** levels.

### 7.4 Economical
- Typically **less expensive** to design and execute than structural test cases
- Fewer test cases needed (due to partitioning)

---

## 8. Functional vs Structural Testing — Key Difference

| Aspect | Functional Testing | Structural Testing |
|--------|-------------------|-------------------|
| **Source** | Specification | Source code |
| **Visibility** | Black-box (no code view) | White-box (code view) |
| **Best for** | Missing logic faults | Incorrect logic faults |
| **Granularity** | Unit → System | Unit, Integration |
| **Can find** | Unimplemented features | Wrong implementations |
| **Cannot find** | Bugs in code not in spec | Code that was never written |

## 9. Steps: From Specification to Test Cases

### Step 1 — Decompose the Specification
Break large specifications into **independently testable features**.

> Example: A word processor spec might be decomposed into: text editing, file save/load, spell check, formatting — each tested independently.

### Step 2 — Select Representatives
For each feature, identify representative values or behaviors:
- Representative **input values** (one per equivalence class)
- **Boundary values** between classes
- **Error cases** (invalid inputs)

### Step 3 — Form Test Specifications
Combine input values to create test specifications.

> For multiple inputs, consider combinations: if input A has 3 classes and input B has 2 classes → potentially 6 test specifications.

### Step 4 — Produce and Execute Actual Tests
Convert test specifications into concrete executable test cases with:
- Exact input values
- Expected output values
- Pass/fail criteria

---

## 10. Example — ZIP Code Lookup

**Specification**:
- Input: ZIP code (5-digit US postal code)
- Output: List of city names for that ZIP code

### Step 1 — Decompose
Single feature: look up cities by ZIP code.

### Step 2 — Select Representatives

**Valid inputs:**
- ZIP with **0 cities** (valid ZIP but no cities listed) — boundary
- ZIP with **1 city** — normal case
- ZIP with **many cities** — boundary

**Malformed inputs (boundary and error):**
- Empty string
- 1–4 characters (too short)
- 5 characters but non-digits (e.g., "1234X")
- 6 characters (too long) — boundary
- Very long string
- Non-character data (e.g., null, binary data)

### Step 3 & 4 — Test Cases

| Test | Input | Expected Output |
|------|-------|----------------|
| T1 | "10001" | ["New York"] (1 city) |
| T2 | "94102" | ["San Francisco"] |
| T3 | "02134" | [multiple cities] |
| T4 | "" | Error: empty input |
| T5 | "1234" | Error: too short |
| T6 | "123456" | Error: too long |
| T7 | "1234X" | Error: non-digit character |
| T8 | "00000" | [] empty list (valid ZIP, no city) |

## 11. Random Testing

**Random testing** generates test inputs **randomly and independently** from the input domain, then uses the specification to determine expected output.

### When There Is No Specification
In the absence of a spec, **crashes or exceptions** during test execution serve as indicators of faults (the program should not crash on any input).

### Advantages
- **Cheap to use** — no manual test design effort
- **No bias** — avoids the designer making the same assumptions as the programmer
- **Sometimes quick** — can accidentally stumble on bugs fast

### Disadvantages
- **Only finds basic bugs** — those triggered by a wide range of inputs
- **Poor performance** compared to systematic techniques for most bugs
- **Low coverage** — unlikely to hit sparse failure regions or boundary conditions

---

## 12. Fuzzing

**Fuzzing** is an automated form of random testing that deliberately generates **invalid, unexpected, or random data** as inputs, then monitors for:
- **Crashes**
- **Failing assertions**
- **Memory leaks**
- **Unexpected exceptions**

### Core Idea
Feed a program many slightly anomalous inputs automatically and observe what breaks — without necessarily knowing what the correct output should be.

### Types of Fuzzing

| Dimension | Options |
|-----------|---------|
| Generation strategy | **Mutation-based** vs **Generation-based** |
| Knowledge of format | **Dumb** (no knowledge) vs **Smart** (some knowledge) |
| Code visibility | **Black-box** vs **Grey-box** vs **White-box** |

---

## 13. Mutation-Based Fuzzing

### How It Works
1. Start with a **valid, well-formed input** (seed)
2. **Randomly perturb** the seed:
   - Flip bits
   - Change bytes
   - Remove or insert characters
   - Shift character values
3. Feed mutated inputs to the program
4. Record any crashes or errors

```
Seed input  →  [mutate]  →  Mutated input  →  Run program  →  Crash? Record it!
  "valid.pdf"       flip bits       "?alid.pdf"
```

### Little or No Format Knowledge Required
The fuzzer does not need to understand the structure of the input — it just perturbs whatever it receives.

### Real-World Example — Fuzzing a PDF Viewer

```
Step 1: Google for .pdf → build a corpus of real PDF files
Step 2: Collect seed PDF files from the corpus
Step 3: Mutate each seed file (flip bits, truncate, swap bytes)
Step 4: Feed mutated PDFs to the PDF viewer
Step 5: Record any crash + the exact input that caused it
Step 6: Report crash-inducing inputs as potential bugs
```

### Pros and Cons

| Pros | Cons |
|------|------|
| Easy to set up and automate | Limited by quality of initial seed corpus |
| Little to no knowledge of format required | May fail for protocols with **checksums** (mutated checksum → rejected before processing) |
| Scales well | May miss bugs requiring structurally valid inputs |

---

## 14. Generation-Based Fuzzing

### How It Works
Instead of mutating existing inputs, **generate test cases from scratch** using a formal description of the input format:
- RFC specifications
- File format documentation
- Protocol grammars

```
Input spec (RFC / grammar)  →  [generator]  →  Generated inputs  →  Run program
```

### Anomaly Injection
Once valid inputs are generated, **anomalies are injected** at every possible position in the input structure — ensuring every field, every length, every boundary is exercised.

### Example Tool: SPIKE (by Immunity)
- Reads protocol specification
- Generates structurally valid inputs
- Injects anomalous values at every protocol field

### Real-World Example — Fuzzing PNG Image Parser

```
PNG spec defines:
  - 8-byte header signature
  - Chunks: [length (4 bytes)][type (4 bytes)][data][CRC (4 bytes)]

Generation-based fuzzer:
  1. Generates valid PNG structure from spec
  2. Injects anomalous values in each field:
     - Negative length values
     - Unknown chunk types
     - CRC mismatches
     - Zero-length data chunks
  3. Feeds each variant to the PNG parser
  4. Records crashes
```

### Pros and Cons

| Pros | Cons |
|------|------|
| **Completeness** — can cover all parts of the format | Writing generators is **hard and time-consuming** |
| Can handle **checksums and complex dependencies** | Quality depends entirely on **quality of the spec** |
| Better structural coverage than mutation | Requires deep knowledge of the input format |

---

## 15. Mutation-Based vs Generation-Based — Summary Comparison

| Aspect | Mutation-Based | Generation-Based |
|--------|---------------|-----------------|
| **Setup effort** | Low | High |
| **Format knowledge needed** | Little to none | Extensive |
| **Handles checksums** | ❌ Fails | ✅ Handles |
| **Initial corpus needed** | ✅ Yes | ❌ No |
| **Coverage quality** | Limited by corpus | Limited by spec quality |
| **Best for** | File formats (PDF, images) | Network protocols, structured formats |
| **Example tools** | ZZUF, FileFuzz, Taof | SPIKE, Peach Fuzzer |

## 16. Connecting the Techniques

```
Specification
     │
     ├──► Functional Testing (Systematic)
     │         │
     │         ├── Equivalence Partitioning
     │         └── Boundary Value Analysis
     │
     └──► Random Testing
               │
               └──► Fuzzing
                         │
                         ├── Mutation-Based
                         └── Generation-Based
```

| Technique | Input Source | Systematic? | Finds Missing Logic? | Handles Complex Formats? |
|-----------|-------------|-------------|---------------------|--------------------------|
| Functional Testing | Specification | ✅ Yes | ✅ Yes | ✅ Yes |
| Random Testing | Random | ❌ No | ❌ No | ❌ No |
| Mutation Fuzzing | Seed corpus | Partially | ❌ No | ❌ (checksums) |
| Generation Fuzzing | Format spec | Partially | ❌ No | ✅ Yes |

## 17. Summary

| Concept | One-line Definition |
|---------|-------------------|
| **Functional testing** | Derive test cases from specifications, not code (black-box) |
| **Random testing** | Generate inputs uniformly at random; unbiased but low effectiveness |
| **Equivalence partitioning** | Divide input domain into classes; one representative per class |
| **Boundary value analysis** | Test at edges of equivalence classes where bugs concentrate |
| **Fuzzing** | Automated random testing with anomalous inputs; monitors for crashes |
| **Mutation-based fuzzing** | Perturb a valid seed input; no format knowledge needed |
| **Generation-based fuzzing** | Generate inputs from a format spec; handles complex dependencies |
| **Missing logic fault** | A bug where required functionality was simply never implemented |
| **Quasi-partition** | Input classes that may overlap; still covers the whole space |

### Three Core Takeaways

1. **Random testing is insufficient for finding sparse bugs** — failures cluster in specific regions of the input space. Functional testing draws systematic "lines" around those regions.

2. **Equivalence partitioning + boundary value analysis** is the foundation of functional testing — partition the input space, then test at the edges of each partition where bugs are most likely.

3. **Fuzzing automates random testing at scale** — mutation-based fuzzing is easy to set up but limited by corpus quality; generation-based fuzzing is more thorough but requires deep format knowledge.
