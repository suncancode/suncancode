# Structural Testing

---

## 1. What is Structural Testing?

**Structural testing** judges the thoroughness of a test suite based on the **structure of the program itself** — specifically its source code and control flow.

Also known as:
- **White-box testing** — you can see inside the code
- **Glass-box testing** — transparent view of implementation
- **Code-based testing** — test cases derived from code structure

### Key Distinction from Functional Testing

| | Functional Testing | Structural Testing |
|--|-------------------|-------------------|
| **Source** | Specification (black-box) | Source code (white-box) |
| **Finds** | Missing logic (forgotten features) | Untested code paths |
| **Measure** | Spec coverage | Code coverage |
| **Can test** | What program *should* do | What program *actually does* |

> Important: Structural testing can still test functionality against specifications — but it **adds** test cases that may not be identified from specifications alone.

---

## 2. Why Structural Testing?

### Core Rationale
> *"If part of a program is not executed by any test case, faults in that part cannot be exposed."*

This answers the question: **"What is missing in our test suite?"**

### What counts as a "part"?
Control flow elements in the CFG:
- **Statements** (CFG nodes)
- **Branches** (CFG edges)
- **Conditions** (individual boolean sub-expressions)
- **Paths** (sequences of nodes/edges from entry to exit)

### Complements Functional Testing
Both approaches are needed because they catch **different classes of faults**:

```
Functional testing catches:   Missing logic (code never written)
Structural testing catches:   Untested branches (code written but never run)

Example:
  Spec says: handle case A, B, C
  Code implements: A, B, C, D  ← D is extra, not in spec

  Functional testing: tests A, B, C → misses D entirely
  Structural testing: sees D in code → forces a test for D
```

---

## 3. No Guarantees — What Coverage Cannot Promise

Executing all control flow elements does **NOT** guarantee finding all faults. Two reasons:

### Reason 1: Faulty statement may not corrupt state
A bug in a statement may not manifest as a failure for certain data values.

```c
int result = x / y;   // Bug: y could be 0
                      // But if y=2 in every test → never fails
```

### Reason 2: Corrupt state may not propagate
Even if state is corrupted, a downstream protection mechanism may prevent the failure from being observable.

```c
int val = compute();   // Returns wrong value under some input
if (val < 0) val = 0;  // Protection: clamps negative values
use(val);              // Failure masked — never observed
```

### What Coverage Does Give You
- **Increases confidence** in thoroughness of testing
- **Removes obvious inadequacies** — untested code is definitively a gap
- **Progress indicator** — measurable, tool-supported metric

> Coverage is a **necessary but not sufficient** condition for a good test suite.

---

## 4. Practical Workflow — How to Use Structural Testing

> **Create functional test suite first, THEN measure structural coverage to identify gaps.**

```
Step 1: Write test cases from specification (functional/black-box)
              ↓
Step 2: Run coverage tool (Istanbul, JaCoCo, Coverage.py...)
              ↓
Step 3: Identify unexecuted elements
              ↓
Step 4: Interpret WHY they are unexecuted:
  Case A: Natural spec-implementation divergence (acceptable)
  Case B: Spec doesn't cover something the code does → improve spec
  Case C: Code diverges radically from spec → fix code or spec
  Case D: Functional tests are inadequate → add more tests
              ↓
Step 5: Add test cases to cover gaps → repeat
```

### Warning About Coverage as a Completion Criterion
Coverage measurements are convenient progress indicators, but:
> Using coverage as a *completion criterion* is dangerous — it's easy to achieve high coverage with trivial tests that don't meaningfully verify behavior.

## 5. Statement Coverage (C0)

### Definition
Every **executable statement** (or node in the CFG) must be executed at least once.

```
Coverage = (# executed statements) / (# total statements)
```

### Rationale
> A fault in a statement can only be revealed by executing that statement.  
> If a statement is never run, any bug in it is invisible.

### Statements vs Basic Blocks
- **Basic block**: a sequence of statements with a single entry and single exit — no branches inside
- **Node coverage** = **block coverage** ≈ **statement coverage** (same concept, different granularity)
- 100% node coverage ↔ 100% statement coverage

### Example — `cgi_decode` Function

```
Test suite T0 = {"", "test", "test+case%1Dadequacy"}
→ 17/18 statements executed = 94% statement coverage

Test suite T1 = {"adequate+test%0Dexecution%7U"}
→ 18/18 statements executed = 100% statement coverage

Test suite T2 = {"%3D", "%A", "a+b", "test"}
→ 18/18 statements executed = 100% statement coverage
```

### Coverage ≠ Number of Test Cases
- T1 has **fewer** test cases than T0, but **higher** coverage
- T2 has **more** test cases than T1, but **same** coverage

> More tests ≠ more coverage. Quality of test inputs matters more than quantity.

---

## 6. The Limitation of Statement Coverage

Statement coverage can be **100% but still miss important cases**.

### Example

```c
// Original code:
if (c == '%') {               // D: check for %
    int digit_high = ...;     // F: process hex
    int digit_low = ...;      // G: process hex
    if (digit_high == -1 || digit_low == -1) {
        ok = 1;               // I: error
    } else {
        *dptr = 16*digit_high + digit_low;  // H: success
    }
}
```

**Suppose block F (the else branch) is removed from code.**

With test suite T3 = `{"", "+%0D+%4J"}`:
- 100% statement coverage ✅
- But the **FALSE branch from D** (when `c != '%'`) is never tested ❌

→ A bug in that missing branch would never be detected despite 100% statement coverage!

---

## 7. Branch Coverage (C1)

### Definition
Every **branch** (edge in the CFG) must be executed at least once — meaning every decision must evaluate to both TRUE and FALSE at least once.

```
Coverage = (# executed branches) / (# total branches)
```

### Example

```
T3 = {"", "+%0D+%4J"}
→ 100% Statement Coverage
→ 88% Branch Coverage (7/8 branches) — missing FALSE branch from D

T2 = {"%3D", "%A", "a+b", "test"}
→ 100% Statement Coverage
→ 100% Branch Coverage (8/8 branches) ✅
```

### Branch Subsumes Statement

> **Branch coverage (C1) subsumes Statement coverage (C0)**

Proof: If every edge in the CFG is traversed, every node must be visited.  
The converse is NOT true: 100% statement coverage does NOT imply 100% branch coverage (T3 proves this).

```
Branch Coverage ⊇ Statement Coverage
(C1 is strictly stronger than C0)
```

### Practical Relevance
This is why **C1 is the standard minimum** in most industry projects:
- It catches off-by-one errors in conditionals
- It ensures both TRUE and FALSE paths of every `if` are tested
- Tools (JaCoCo, Istanbul, etc.) support it natively

---

## 8. The Limitation of Branch Coverage

Branch coverage can be 100% but still miss bugs in **individual conditions** within compound expressions.

### Example

```c
// Original (correct):
if (digit_high == -1 || digit_low == -1) { ok = 1; }

// Faulty version (missing negation in first condition):
if (digit_high == 1 || digit_low == -1) { ok = 1; }
```

A branch-adequate test suite can satisfy 100% branch coverage by **only varying `digit_low`**:
- Test where `digit_low == -1` → branch TRUE
- Test where `digit_low != -1` → branch FALSE

In both tests, `digit_high == 1` (the faulty sub-expression) **never determines the result** → bug is never caught despite 100% branch coverage!

---

## 9. Condition Coverage

### Motivation
Branch coverage only checks the **final outcome** of a compound boolean expression — not whether each individual sub-condition was properly tested.

### Basic Condition Coverage
Each **individual condition** (atomic boolean sub-expression) must evaluate to both TRUE and FALSE at least once.

```
Coverage = (# truth values taken by all basic conditions) / (2 × # basic conditions)
```

### Example

```c
if (digit_high == -1 || digit_low == -1)
```

Has **2 basic conditions**:
1. `digit_high == -1`
2. `digit_low == -1`

Basic condition coverage requires:
- `digit_high == -1` must be TRUE in at least one test
- `digit_high == -1` must be FALSE in at least one test
- `digit_low == -1` must be TRUE in at least one test
- `digit_low == -1` must be FALSE in at least one test

### Basic Condition vs Branch — NOT Comparable!

```
T4 = {"first+test%9Ktest%K9"}
→ Satisfies basic condition coverage ✅
→ Does NOT satisfy branch coverage ❌
  (expression "digit_high == -1 || digit_low == -1" is always TRUE)
```

> Basic condition coverage and branch coverage are **incomparable** — neither subsumes the other!

---

## 10. Compound Condition Coverage

### Branch + Condition Coverage
Combines both: cover all branches AND all individual conditions.

### Compound Condition Coverage
Cover **all possible evaluations** of each compound boolean expression.

For `A || B` with 2 conditions → 4 combinations: (T,T), (T,F), (F,T), (F,F)

### The Exponential Problem

For a complex expression like:
```c
(((a || b) && c) || d) && e
```

Full compound condition coverage requires **13 test cases** just for this one expression!

With short-circuit evaluation, some combinations are unreachable, but the number can still be unmanageable.

> For `n` conditions in a compound expression → up to **2ⁿ combinations** → exponential explosion!

This is why compound condition coverage is **rarely used in practice** for complex expressions.

## 11. Path Coverage

### Definition
Every **path** from entry to exit through the program must be executed at least once.

```
Coverage = (# executed paths) / (# total paths)
```

### The Fundamental Problem — Infinite Paths

Programs with loops have **unbounded numbers of paths**:
```
while (condition) {
    // loop body
}
```
The loop can execute 0, 1, 2, 3, ... times → infinitely many paths.

→ **Simple path coverage is usually impossible to satisfy.**

### Solution: Partition Paths into Finite Classes

Three practical strategies to limit paths:
1. **Limit loop traversals** (e.g., 0, 1, more than 1)
2. **Limit path length** (e.g., only paths up to length k)
3. **Limit path dependencies** (e.g., only independent paths)

---

## 12. Boundary Interior Path Testing

### Idea
Group together paths that **differ only in how many times** they repeat a loop body — treat all loop repetitions as equivalent.

**Rule**: Follow each path in the CFG up to the **first repeated node**. The set of paths from root to each leaf in this unrolled tree is the required set.

### What This Captures
- The path that **skips** the loop (0 iterations)
- Each distinct path through the loop body (1 iteration)
- The path that **repeats** the loop (identified but not exhaustively enumerated)

### Limitation
Even without loops, the number of paths can grow exponentially:

```c
if (a) { S1; }
if (b) { S2; }
if (c) { S3; }
...
if (x) { Sn; }
```

With N independent `if` statements → **2ᴺ paths** to traverse.

Additionally, choosing input data to **force a specific path** can be very difficult or impossible when conditions are not independent.

---

## 13. Loop Boundary Adequacy

### Definition
A practical, less stringent alternative to boundary/interior path testing.

A test suite satisfies **loop boundary adequacy** if for every loop in the program, there exist test cases that exercise:

1. **Zero iterations** — the loop body is skipped entirely
2. **One iteration** — the loop body executes exactly once
3. **More than one iteration** — the loop body executes multiple times

### Why These Three Cases?
These correspond to the cases analyzed in a **formal correctness proof** for a loop:
- Zero iterations: verify the loop exit condition is correct when no work is done
- One iteration: verify the loop body works correctly in isolation
- More than one: verify the loop correctly handles continuation and state accumulation

### Example — `while` loop in `cgi_decode`

```c
while (*eptr) {       // loop over each character in encoded string
    char c = *eptr;
    // ... process c ...
    ++eptr;
}
```

Loop boundary adequacy requires:
- T_zero: `encoded = ""` → loop iterates 0 times
- T_one: `encoded = "a"` → loop iterates exactly 1 time
- T_many: `encoded = "abc"` → loop iterates 3 times

## 14. Coverage Criteria Hierarchy

```
Path Coverage
      ⊇
Branch + Condition Coverage
      ⊇
Branch Coverage (C1)         ⊇  Basic Condition Coverage
      ⊇                              (not comparable with C1)
Statement Coverage (C0)
```

| Criterion | Also known as | Subsumes | Industry use |
|-----------|--------------|---------|-------------|
| Statement | C0, node coverage | — | Minimum baseline |
| Branch | C1, decision coverage | C0 | Standard in most projects |
| Basic Condition | — | Neither C0 nor C1 alone | Used with branch |
| Branch + Condition | — | C0, C1, basic condition | Safety-critical systems |
| Compound Condition | — | All above | Rarely used (exponential) |
| Path | — | All above | Rarely feasible |
| Loop Boundary | — | Practical subset of path | Common in unit testing |

## 15. Structural Testing in Practice — Key Points

### When to Use Which Criterion

| Context | Recommended Criterion |
|---------|----------------------|
| General industry development | C1 (branch coverage) |
| Safety-critical systems (aviation, medical) | Branch + Condition (MC/DC) |
| Unit testing loops | Loop boundary adequacy |
| Quick smoke test | C0 (statement coverage) |
| Academic/research | Path, compound condition |

### MC/DC — Modified Condition/Decision Coverage
Used in **safety-critical** standards (DO-178C for aviation, IEC 61508):
- Each condition independently affects the decision outcome
- Stronger than basic condition, weaker than compound condition
- Manageable number of test cases (linear, not exponential)

### The Right Workflow

```
1. Write functional tests from specification
         ↓
2. Measure C1 (branch coverage)
         ↓
3. Find uncovered branches
         ↓
4. Ask: WHY is this branch uncovered?
   a. Dead code?          → Remove it or document why
   b. Spec doesn't cover? → Add to spec, add test
   c. Poor functional tests? → Improve tests
         ↓
5. Add targeted tests for uncovered branches
         ↓
6. Repeat until coverage target met
```

---

## 16. Summary

| Concept | One-line Definition |
|---------|-------------------|
| **Structural testing** | Judge test thoroughness based on code structure, not specification |
| **Statement coverage (C0)** | Every executable statement executed at least once |
| **Branch coverage (C1)** | Every branch (TRUE and FALSE) of every decision exercised |
| **Basic condition coverage** | Each atomic boolean condition takes both TRUE and FALSE values |
| **Compound condition coverage** | All combinations of condition truth values in a compound expression |
| **Path coverage** | Every path from entry to exit executed at least once |
| **Boundary interior testing** | Group paths by loop repetition pattern; test each pattern |
| **Loop boundary adequacy** | Test every loop with 0, 1, and >1 iterations |
| **Subsumption** | C1 ⊇ C0: branch coverage automatically gives statement coverage |

### Three Core Takeaways

1. **C1 (branch coverage) is the practical standard** — it subsumes C0, catches more bugs than statement coverage alone, and is directly supported by all major coverage tools. Use it as your default minimum.

2. **Coverage is necessary but not sufficient** — 100% branch coverage does not mean 100% correct. Faulty statements may not corrupt observable state, and corrupt state may not propagate to failure. Coverage removes *obvious inadequacies*, not all inadequacies.

3. **Structural + Functional = complete testing strategy** — functional testing catches missing logic (code that was never written); structural testing catches untested logic (code that was written but never run). Neither alone is sufficient; use both in combination.
