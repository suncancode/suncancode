# Combinatorial Testing

---

## 1. Learning Objectives

- Understand the rationale and basic approach for **systematic combinatorial testing**
- Learn how to apply three representative approaches:
  - **Category-Partition Testing**
  - **Pairwise Combination Testing**
  - **Catalog-Based Testing**
- Understand key differences, similarities, and suitable application domains for each approach

---

## 2. Basic Idea — Why Combinatorial Testing?

### The Problem
Real programs have multiple input parameters, each with multiple possible values. Testing all combinations exhaustively is **impossible** in practice.

**Example — Web Browser Configuration:**

| Attribute | Values |
|-----------|--------|
| Browser | Chrome, Firefox |
| OS | Windows, MacOS, Android |

Full combination: 2 × 3 = **6 test cases** (manageable here)

But real systems easily reach **millions of combinations**.

### The Core Idea
1. Identify **distinct attributes** that can be varied (in data, environment, or configuration)
2. **Systematically generate combinations** to be tested — not all, but a smart subset
3. Rationale: test cases should be **varied** and include possible **corner cases**

### Three Approaches Compared

| Approach | Key Idea |
|----------|---------|
| **Category-Partition** | Manually identify values per category, then automatically generate combinations |
| **Pairwise Testing** | Cover all pairs of values (not all combinations) — much smaller test suite |
| **Catalog-Based** | Use recorded experience (catalogs) to identify important values systematically |

---

## 3. Category-Partition Testing

### Overview
Separates the test design process into two steps:
- **Manual step**: identify categories and values (creative, requires human judgment)
- **Automatic step**: generate all combinations (mechanical, can be tool-assisted)

### The 3-Step Process

---

### Step 1 — Decompose Specification and Identify Categories

**1a. Decompose** the specification into **independently testable features**.

**1b. For each feature, identify:**
- **Parameters**: inputs the function takes
- **Environment elements**: external factors that affect behavior (e.g., database state)

**1c. For each parameter and environment element, identify elementary characteristics called categories.**

> Choosing categories is NOT trivial — it requires experience and knowledge of the application domain. The test designer must look **under the surface** of the specification to find hidden characteristics.

---

### Step 2 — Identify Relevant Values

For each category, identify representative value classes:

| Value Type | Description |
|-----------|-------------|
| **Normal values** | Typical valid inputs within the expected range |
| **Boundary values** | Extreme values within a class; values just outside |
| **Special values** | Unusual but valid inputs (e.g., 0, 1, empty) |
| **Error values** | Invalid inputs that should trigger error handling |

> Important: At this step, **ignore interactions** among values from different categories — these are handled in Step 3.

---

### Step 3 — Introduce Constraints

Without constraints, the number of combinations explodes. Three types of constraints reduce this:

#### [error] Constraint
Marks a value class as erroneous — only needs to be tested **once**, not in combination with everything else.

> Rationale: Handling an error case typically bypasses other program logic, so combining errors with other values adds no testing value.

#### [property] / [if-property] Constraint
Rules out **invalid combinations** between values of different categories.

- `[property X]` — groups values of one parameter into a named subset
- `[if X]` — restricts which values of another parameter can be combined with this group

> Example: "Number of required components = number of required slots" only makes sense **if** the model actually has required slots (RSMANY).

#### [single] Constraint
Marks a value class to be tested only **once** to reduce test suite size — not because it's an error, but as a design choice to reduce combinatorial explosion.

> Difference from [error]: [single] is a size-reduction choice; [error] reflects a real program logic bypass. They have the same mechanical effect but differ in rationale and documentation.

---

### Full Example — Check Configuration

**Specification**: Check the validity of a computer configuration (model + set of components).

**Parameters**:
- `Model`: identifies a product; has required and optional slots
- `Components`: a set of (slot, component) pairs

**Environment**:
- `Product database`: contains all valid models and components

---

#### Step 1 — Categories Identified

**Parameter: Model**
- Model number
- Number of required slots (#SMRS)
- Number of optional slots (#SMOS)

**Parameter: Components**
- Correspondence of selection with model slots
- Number of required components with non-empty selection
- Required component selection
- Number of optional components with non-empty selection
- Optional component selection

**Environment: Product database**
- Number of models in database (#DBM)
- Number of components in database (#DBC)

---

#### Step 2 — Values Per Category

**Model number:** `Malformed | Not in database | Valid`

**#SMRS (required slots):** `0 | 1 | Many`

**#SMOS (optional slots):** `0 | 1 | Many`

**Correspondence with slots:** `Omitted slots | Extra slots | Mismatched slots | Complete correspondence`

**# required components selected:** `0 | < #SMRS | = #SMRS`

**Required component selection:** `Some defaults | All valid | ≥1 incompatible with slots | ≥1 incompatible with another | ≥1 incompatible with model | ≥1 not in database`

**# optional components selected:** `0 | < #SMOS | = #SMOS`

**Optional component selection:** `Some defaults | All valid | ≥1 incompatible with slots | ≥1 incompatible with another | ≥1 incompatible with model | ≥1 not in database`

**#DBM:** `0 | 1 | Many`

**#DBC:** `0 | 1 | Many`

> Raw combinations (no constraints): **3 × 3 × 3 × 4 × 3 × 6 × 3 × 6 × 3 × 3 = 314,928 test cases**

---

#### Step 3 — Applying Constraints

**After [error] constraints** (marking invalid/error values as [error]):

```
Model number:          Malformed [error], Not in database [error], Valid
Correspondence:        Omitted [error], Extra [error], Mismatched [error], Complete
# required selected:   0 [error], < #SMRS [error], = #SMRS
# not in database:     [error]
#DBM:                  0 [error]
#DBC:                  0 [error]
```

→ **314,928 → 2,711 test cases**

**After [property] constraints** (ruling out logically impossible combinations):

```
#SMRS: 1 [property RSNE], Many [property RSNE][property RSMANY]
#SMOS: 1 [property OSNE], Many [property OSNE][property OSMANY]
# required selected = #SMRS  [if RSMANY]
# optional selected < #SMOS  [if OSNE]
```

→ **2,711 → 908 test cases**

**After [single] constraints** (reducing further by testing edge values only once):

```
#SMRS: 0 [single], 1 [single]
#SMOS: 0 [single], 1 [single]
Required selection: Some defaults [single]
Optional selection: Some defaults [single]
#DBM: 1 [single]
#DBC: 1 [single]
```

→ **908 → 69 test cases**

**Summary of constraint effect:**

```
No constraints:          314,928 test cases
After [error]:             2,711 test cases   (99.1% reduction)
After [property]:            908 test cases
After [single]:               69 test cases   (99.98% total reduction)
```

## 4. Pairwise Combinatorial Testing

### Motivation
Category-partition testing without many constraints can still yield an unmanageable number of test cases. **Pairwise testing** provides a systematic way to drastically reduce the test suite.

### Key Rationale
> Most failures are triggered by **single values** or **interactions between two** (or a few) parameters — not by interactions of all parameters simultaneously.

Therefore: instead of covering all combinations, **cover all pairs of values** across every pair of parameters.

### Exhaustive vs Pairwise

| Approach | Coverage | Test Cases |
|----------|---------|-----------|
| Exhaustive | All combinations | Exponential |
| Pairwise | All pairs | Much smaller (often O(v² log n)) |
| N-way | All n-tuples | Between pairwise and exhaustive |

### Example — Display Control

**5 parameters:**

| Parameter | Values |
|-----------|--------|
| Display Mode | full-graphics, text-only, limited-bandwidth |
| Language | English, French, Spanish, Portuguese |
| Fonts | Minimal, Standard, Document-loaded |
| Color | Monochrome, Color-map, 16-bit, True-color |
| Screen Size | Hand-held, Laptop, Full-size |

**Exhaustive combinations:** 3 × 4 × 3 × 4 × 3 = **432 test cases**

**Pairwise combinations:** only **17 test cases** needed to cover all pairs!

### Pairwise Test Suite (17 test cases)

| # | Language | Color | Display Mode | Fonts | Screen Size |
|---|----------|-------|-------------|-------|------------|
| 1 | English | Monochrome | Full-graphics | Minimal | Hand-held |
| 2 | English | Color-map | Text-only | Standard | Full-size |
| 3 | English | 16-bit | Limited-bandwidth | — | Full-size |
| 4 | English | True-color | Text-only | Document-loaded | Laptop |
| 5 | French | Monochrome | Limited-bandwidth | Standard | Laptop |
| 6 | French | Color-map | Full-graphics | Document-loaded | Full-size |
| 7 | French | 16-bit | Text-only | Minimal | — |
| 8 | French | True-color | — | — | Hand-held |
| 9 | Spanish | Monochrome | — | Document-loaded | Full-size |
| 10 | Spanish | Color-map | Limited-bandwidth | Minimal | Hand-held |

| 17 | Portuguese | True-color | Limited-bandwidth | Standard | Hand-held |

> Every pair of values from any two parameters appears in at least one row.  
> Reduction: 432 → 17 test cases (**96% reduction**)

### Adding Constraints to Pairwise

Simple constraints (e.g., "Monochrome color is only compatible with Hand-held screen") can be handled by **splitting into separate sub-tables** — one for the constrained case and one for the unconstrained case.

## 5. Catalog-Based Testing

### Motivation
Identifying good value classes requires **human judgment and experience**. Catalog-based testing systematizes this experience by recording **standard patterns** for each type of variable or program element.

> A catalog is a collection of test case specifications for common types of elements — so testers don't have to reinvent the wheel every time.

### Benefits of Catalogs
- Speed up the test design process
- Routinize many decisions, focusing human effort on creative tasks
- Accelerate training of new testers
- Reduce human error

### Catalog-Based Testing Process

**Step 1**: Analyze the specification to identify simple elements:
- **Pre-conditions (PRE)**: conditions on inputs that must be true before execution
  - *Validated*: checked by the system
  - *Assumed*: assumed true; not checked
- **Post-conditions (POST)**: results/effects of the execution
- **Variables (VAR)**: elements used in computation
- **Definitions (DEF)**: abbreviations or domain concepts
- **Operations (OP)**: main operations performed

**Step 2**: Derive an initial set of test case specifications from PRE, POST, and DEF.

**Step 3**: Complete and refine the test suite by applying catalog entries to each identified element.

---

### The Standard Catalog

#### Part I

| Element Type | Test Case Specifications |
|-------------|------------------------|
| **Boolean** | True (in/out), False (in/out) |
| **Enumeration** | Each enumerated value (in/out), Some value outside the set (in) |
| **Range L...U** | L-1 (in), L (in/out), A value between L and U (in/out), U (in/out), U+1 (in) |
| **Numeric Constant C** | C (in/out), C-1 (in), C+1 (in), Any other constant compatible with C (in) |

#### Part II

| Element Type | Test Case Specifications |
|-------------|------------------------|
| **Non-Numeric Constant C** | C (in/out), Any other constant compatible with C (in), Some other compatible value (in) |
| **Sequence** | Empty (in/out), Single element (in/out), More than one element (in/out), Maximum length (in/out), Longer than maximum (in), Incorrectly terminated (in) |
| **Scan with action on pattern P** | P at beginning, P in interior, P at end, PP contiguously, P not present, Proper prefix of P at end |

> `in` = applies only as input; `out` = applies only as output; `in/out` = applies to both

---

### Full Example — `cgi_decode` Function

**Specification**: `cgi_decode` translates a CGI-encoded string to plain ASCII:
- `+` → space
- `%xy` (where x, y are hex digits) → ASCII character with value `xy`
- Other alphanumeric characters → copied as-is
- Returns `0` for success, `1` for malformed input

---

#### Step 1 — Identify Simple Elements

**Variables:**
- VAR 1: `encoded` — input string of ASCII characters
- VAR 2: `decoded` — output string of ASCII characters
- VAR 3: return value — boolean (0 or 1)

**Definitions:**
- DEF 1: hexadecimal characters — `['0'..'9', 'A'..'F', 'a'..'f']`
- DEF 2: sequences `%xy` where x, y are hex characters
- DEF 3: CGI items — alphanumeric character, or `+`, or CGI hexadecimal (`%xy`)

**Operations:**
- OP 1: Scan `encoded`

**Pre-conditions:**
- PRE 1 (Assumed): `encoded` is a null-terminated string
- PRE 2 (Validated): `encoded` is a sequence of CGI items

**Post-conditions:**
- POST 1: alphanumeric characters copied to output
- POST 2: `+` replaced by ASCII SPACE
- POST 3: `%xy` replaced by corresponding ASCII character
- POST 4: returns 0 on success
- POST 5: returns 1 if `%xy` is malformed (x or y absent or not hex)
- POST 6: returns 1 if any illegal character present

---

#### Step 2 — Initial Test Cases from PRE and POST

From **PRE 2** (validated — 2 classes):
- TC-PRE2-1: `encoded` is a valid sequence of CGI items
- TC-PRE2-2: `encoded` is NOT a valid sequence of CGI items

From **POST 1**:
- TC-POST1-1: `encoded` contains alphanumeric characters
- TC-POST1-2: `encoded` does NOT contain alphanumeric characters

From **POST 2**:
- TC-POST2-1: `encoded` contains `+`
- TC-POST2-2: `encoded` does NOT contain `+`

From **POST 3**:
- TC-POST3-1: `encoded` contains CGI hexadecimals (`%xy`)
- TC-POST3-2: `encoded` does NOT contain a CGI hexadecimal

From **POST 5**:
- TC-POST5-1: `encoded` contains erroneous CGI hexadecimals

From **POST 6**:
- TC-POST6-1: `encoded` contains illegal characters

---

#### Step 3 — Apply Catalog Entries

**Catalog entry: Boolean** → applies to return value (VAR 3)
- Generates: True, False → already covered by TC-PRE2-1 and TC-PRE2-2 ✅

**Catalog entry: Enumeration** → applies to CGI item (DEF 3)
- Covered by TC-POST1-x, TC-POST2-x, TC-POST3-x ✅

**Catalog entry: Enumeration** → applies also to improper CGI hexadecimals → **new cases:**
- TC-POST5-2: `encoded` terminated with `%x` (x is hex, y missing)
- TC-POST5-3: `encoded` contains `%ky` (k not hex, y is hex)
- TC-POST5-4: `encoded` contains `%xk` (x is hex, k not hex)
- Old TC-POST5-1 can be eliminated (less specific than new cases)

**Catalog entry: Range** → applies to hex digits (DEF 1):
- Test boundary characters around `0`, `9`, `A`, `F`, `a`, `f`
- Characters just before and after each range: `/`, `:`, `@`, `G`, `` ` ``, `g`
- → **30 new test cases** (15 per character position in `%xy`)

**Catalog entry: Sequence** → applies to `encoded` (VAR 1), `decoded` (VAR 2), CGI item (DEF 2):
- Non-redundant new cases for `encoded`:
  - TC-VAR1-1: empty sequence
  - TC-VAR1-2: sequence of length one
  - TC-VAR1-3: very long sequence
- Non-redundant new cases for CGI item:
  - `%` terminated sequence
  - `%` initiated sequence
  - sequence including `%xyz` (three hex chars — boundary)

**Catalog entry: Scan with pattern** → applies to OP 1 (scan `encoded`):
- Generates 17 test cases; 10 are non-redundant:
  - TC-OP1-1: `encoded` starts with alphanumeric
  - TC-OP1-2: `encoded` starts with `+`
  - TC-OP1-3: `encoded` starts with `%xy`
  - TC-OP1-4: `encoded` terminates with alphanumeric
  - TC-OP1-5: `encoded` terminates with `+`
  - TC-OP1-6: `encoded` terminates with `%xy`
  - TC-OP1-7: `encoded` contains two consecutive alphanumeric chars
  - TC-OP1-8: `encoded` contains `++`
  - TC-OP1-9: `encoded` contains `%xy%zw`
  - TC-OP1-10: `encoded` contains `%x%yz`

## 6. Comparing the Three Approaches

| Aspect | Category-Partition | Pairwise | Catalog-Based |
|--------|-------------------|---------|--------------|
| **Manual step** | Identify categories and values | Same as category-partition | Use catalog to identify values |
| **Automatic step** | Generate all combinations | Generate pair-covering combinations | Apply catalog entries mechanically |
| **Constraint handling** | [error], [property], [single] | Separate sub-tables | Implicit in catalog entries |
| **Test suite size** | Can be large without constraints | Small (O(v² log n)) | Depends on catalog coverage |
| **Human effort** | High (creative judgment) | Lower (guided by algorithm) | Medium (catalog guides decisions) |
| **Best for** | Complex specs with clear constraints | Large parameter spaces | Reusable patterns, standardized domains |
| **Combinatorial focus** | All combinations (constrained) | All pairs | N/A (values, not combinations) |

---

## 7. Combining the Approaches (Best Practice)

The three approaches are **complementary**, not mutually exclusive:

```
Step 1: Use CATALOG-BASED testing
        → systematically identify important value classes
        → guided by recorded experience, not just intuition
              ↓
Step 2: Apply CATEGORY-PARTITION
        → organize values into categories
        → apply [error], [property], [single] constraints
        → reduce combination space
              ↓
Step 3: Apply PAIRWISE testing
        → if combinations still too many after constraints
        → generate pair-covering subset
        → achieves high fault detection with small test suite
```

## 8. Summary

| Concept | One-line Definition |
|---------|-------------------|
| **Combinatorial testing** | Systematically test combinations of distinct attributes |
| **Category** | An elementary characteristic of a parameter or environment element |
| **Value class** | A group of values expected to behave similarly |
| **[error] constraint** | Marks a value as erroneous — test only once, not in all combinations |
| **[property] constraint** | Groups values and restricts which combinations are valid |
| **[single] constraint** | Test only once to reduce suite size — not an error, just a design choice |
| **Pairwise testing** | Cover all pairs of values from any two parameters — not all combinations |
| **N-way testing** | Cover all n-tuples — generalization of pairwise |
| **Catalog** | A recorded collection of important test cases for each type of variable |
| **PRE/POST/DEF/VAR/OP** | Elements extracted from spec in catalog-based testing |

### Three Core Takeaways

1. **Exhaustive combination testing is infeasible** — the number of combinations grows exponentially with parameters. Constraints ([error], [property], [single]) are essential to reduce the space from hundreds of thousands to dozens of test cases.

2. **Pairwise testing is the practical solution for large parameter spaces** — most bugs are triggered by one or two parameter interactions, so covering all pairs catches most faults with a dramatically smaller test suite (e.g., 432 → 17 test cases).

3. **Catalogs systemize human expertise** — instead of reinventing value classes from scratch every time, catalogs encode proven patterns (boundary values for ranges, all values for enumerations, empty/single/long for sequences) so testers can focus creative effort on truly novel aspects of each specification.
