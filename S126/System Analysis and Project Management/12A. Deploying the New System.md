## PART I — Testing

### The Big Picture: Why Testing?

> Building a system that *works on the developer's machine* is not enough.
> Testing ensures the system works correctly **for real users, in real conditions**.

Think of it as the difference between:
- A chef tasting their own food while cooking (**unit testing**)
- A restaurant critic eating the full meal (**system testing**)
- Real customers dining and giving feedback (**user acceptance testing**)

---

### Core Testing Concepts

#### Testing
> **Testing** = the process of examining a component, subsystem, or system to determine its operational characteristics and whether it contains any **defects**.

#### Test Case
> **Test case** = a formal description of:
> - A **starting state**
> - One or more **events** the software must respond to
> - The **expected response** or ending state

**Two rules for test cases:**
1. Must be defined based on well-understood **functional and non-functional requirements**
2. Must test **all normal AND exception situations**
   - Normal: What happens when everything goes right?
   - Exception: What happens when something goes wrong?

#### Test Data
> **Test data** = the set of starting states and events used to execute a test case — the actual data fed into the system during testing.

```
Test Case ──────────────────────────────► Defines WHAT to test
                                          (starting state + events + expected result)
Test Data ──────────────────────────────► Provides the ACTUAL INPUT
                                          (the data used to run the test case)
```

---

### The Testing Hierarchy — From Small to Large

Testing is done in layers, starting small and expanding outward:

```
Unit Testing          ← Test one method/class at a time
      │
      ▼
Integration Testing   ← Test groups of components working together
      │
      ▼
System Testing        ← Test the entire system end-to-end
      │
      ▼
Performance/Stress    ← Test how the system behaves under load
Testing
      │
      ▼
User Acceptance       ← Real users verify the system meets their needs
Testing (UAT)
```

---

### Layer 1: Unit Testing

> **Unit test** = tests of an **individual method, class, or component** before it is integrated with other software.

Because a unit can't run in isolation (it needs other parts), two special tools are used:

| Tool | Definition | Purpose |
|------|-----------|---------|
| **Driver** | A method/class that **simulates the caller** — something that sends a message to the method being tested | "Pretend caller" — tests the method when the real calling code isn't written yet |
| **Stub** | A method/class that **simulates a called method** — something the method under test calls but hasn't been written yet | "Pretend dependency" — replaces unfinished code during testing |

**Memory trick:**
```
DRIVER → Drives the test by calling the unit being tested
         (replaces the code ABOVE in the call chain)

STUB   → Stands in for code that the unit calls
         (replaces the code BELOW in the call chain)
```

**Example:**
```
Testing method: calculateOrderTotal()

DRIVER: A test script that calls calculateOrderTotal() with sample data
        (because the real UI that would call it isn't built yet)

STUB:   A fake getProductPrice() method that always returns $10.00
        (because the real pricing engine isn't built yet)
```

---

### Layer 2: Integration Testing

> **Integration test** = tests of the **behaviour of a group of methods, classes, or components** working together.

When individual units are combined, new problems emerge at the **interfaces** between them. Four common types:

| Problem Type | Description | Example |
|-------------|-------------|---------|
| **Interface incompatibility** | One method passes a wrong data type to another | Method passes a String where an Integer is expected |
| **Parameter value errors** | A method receives or returns an unexpected value | A price field returns a negative number |
| **Run-time exceptions** | A method generates an error due to conflicting resource needs | "Out of memory" or "File already in use" error |
| **Unexpected state interactions** | Two or more objects' states interact to cause complex failures | OnlineCart works correctly for all Customer states except one rare combination |

> 💡 **Key insight:** Unit testing catches bugs *within* a component. Integration testing catches bugs *between* components.

---

### Layer 3: System Testing

> **System test** = an integration test of an **entire system or independent subsystem**.

**When is it done?**
- Can be performed at the **end of each iteration** in iterative development
- Can also be performed more frequently for critical systems

**Scope:** Tests end-to-end workflows, not just individual components.

---

### Layer 4: Performance and Stress Testing

> **Performance test / Stress test** = an integration and usability test that determines whether a system can meet **time-based performance criteria**.

Two key metrics:

| Metric | Definition | Example |
|--------|-----------|---------|
| **Response time** | The desired or maximum allowable time limit for the software to respond to a query or update | "Search results must appear within 2 seconds" |
| **Throughput** | The desired or minimum number of queries/transactions processed per minute or hour | "Must handle 500 simultaneous users" |

> Performance testing answers: *"Does it work fast enough?"*
> Stress testing answers: *"Does it break under heavy load?"*

---

### Layer 5: User Acceptance Testing (UAT)

> **User acceptance test** = a system test performed to determine whether the system **fulfils user requirements**.

**When is it done?**
- Near the end of the project
- At the end of later project iterations in iterative development

**Two levels of formality:**

| Formal UAT | Informal UAT |
|-----------|-------------|
| Very structured — details included in the Request for Proposal (RFP) and procurement contract | Informal — integrated into normal development activities |
| Payments may be **tied to passing tests** | Collaborative, continuous feedback |
| Used in large government/enterprise contracts | Used in smaller/Agile projects |

> UAT is the **final gate** before the system goes live — if real users can't validate it works for them, it doesn't deploy.

## PART II — Deployment Activities

> Note: System tests, stress tests, and UAT are also considered deployment activities — they happen as part of the transition to production.

Deployment involves three major activities beyond testing:

```
Deployment Activities
├── 1. Converting and Initializing Data
├── 2. Training Users
└── 3. Configuring the Production Environment
```

---

### Activity 1: Converting and Initializing Data

> An operational system requires a **fully populated database** to support ongoing processing from day one.

**Where does the initial data come from?**

| Source | Description |
|--------|-------------|
| Files/databases of the **system being replaced** | Migrate data from the old system |
| **Manual records** | Enter data from paper documents |
| Files/databases from **other systems** in the organisation | Pull data from related systems |
| **User feedback** during normal system operation | Collected after go-live |

**Three approaches to data conversion:**

| Approach | Method |
|----------|--------|
| **Reuse existing databases** | Modify or update the existing data in place |
| **Reload databases** | Copy and convert data; export from old DBMS and import into new DBMS |
| **Manual data entry** | Enter data from paper documents into the new system |

> ⚠️ Data conversion is often the most underestimated activity in deployment — legacy data is messy, inconsistent, and requires significant cleaning before it can be loaded into the new system.

---

### Activity 2: Training Users

Two distinct audiences with different training needs:

| Audience | Training Approach | Focus |
|----------|------------------|-------|
| **End users** | Hands-on, formal training required | Specific business processes (e.g., order entry, inventory control, accounting); includes practice exercises, Q&A, one-on-one tutorials |
| **System operators** | Can be less formal — often self-study is sufficient | Experienced operators and administrators can learn through self-study |

**Two types of documentation produced:**

| Document Type | Purpose | Audience |
|--------------|---------|---------|
| **System Documentation** | Describes system requirements and architecture | Developers, maintenance and upgrade teams |
| **User Documentation** | Describes how to interact with and use the system | End users and system operators |

---

### Activity 3: Configuring the Production Environment

Setting up all the infrastructure components needed to run the system in production:
- Servers, networking, databases
- Client machines and software
- Security configurations
- Integration with other systems

*(Example: Infrastructure and client configuration for a Microsoft .NET application)*

## PART III — Planning and Managing Implementation and Deployment

### Development Order

Before deploying, the team must decide the **order in which modules/components are built**. Four strategies:

| Strategy | Description | When to Use |
|----------|-------------|------------|
| **IPO (Input → Process → Output)** | Implement input modules first, then process modules, then output modules | When data flow is the primary structure |
| **Top-down** | Implement top-level (high-level) modules first, then work downward | When architecture/design is clear and stable |
| **Bottom-up** | Implement low-level detailed modules first, then combine upward | When foundational components are complex and uncertain |
| **Use-case driven** | Select specific use cases and order development based on those | When user value delivery is the priority (common in Agile/iterative) |

> 💡 **Package diagrams** showing dependencies constrain development order — a module cannot be built until all modules it depends on are ready.

---

### Deployment Strategies — How to Switch to the New System

Three approaches for transitioning from old system to new:

#### Strategy 1: Direct Deployment (aka "Big Bang")

> **Direct deployment** = install the new system, make it operational immediately, and **shut off the old system at the same time**.

```
OLD SYSTEM  ████████████████|
NEW SYSTEM                  |████████████████████
                         Go-live
```

| Pros | Cons |
|------|------|
| Lower cost | **Higher risk** — no fallback if new system fails |
| Simpler to manage | Users must adapt immediately |
| Fast transition | Problems are immediately visible and critical |

**Best for:** Small systems, low-risk environments, or when old and new systems are fundamentally incompatible.

---

#### Strategy 2: Parallel Deployment

> **Parallel deployment** = run the **old and new systems simultaneously** for an extended period.

```
OLD SYSTEM  ████████████████████████████|
NEW SYSTEM              ████████████████████████
                     Both running
```

| Pros | Cons |
|------|------|
| **Lower risk** — old system is fallback | **Higher cost** — double the infrastructure and effort |
| Results can be compared and validated | Staff must operate both systems |
| Users can learn at their own pace | Data must be entered twice |

**Best for:** Mission-critical systems (banking, healthcare) where downtime or errors are unacceptable.

---

#### Strategy 3: Phased Deployment

> **Phased deployment** = install the new system and make it operational **in a series of steps or phases**.

```
Phase 1: Module A deployed    ████████████
Phase 2: Module B deployed              ████████████
Phase 3: Module C deployed                        ████████████
```

**Examples of phasing:**
- By **geographic location** (deploy to Sydney first, then Melbourne, then Brisbane)
- By **user group** (deploy to sales team first, then marketing, then finance)
- By **module** (deploy order management first, then inventory, then reporting)

| Pros | Cons |
|------|------|
| Manageable risk — smaller scope each phase | Longer overall transition period |
| Problems are contained to one phase | Complexity of running partial old/new systems |
| Team learns and improves between phases | Requires clear phasing plan |

---

### Comparison of Deployment Strategies

| Strategy | Risk | Cost | Speed | Best For |
|----------|------|------|-------|---------|
| **Direct** | High | Low | Fast | Small/low-risk systems |
| **Parallel** | Low | High | Slow | Mission-critical systems |
| **Phased** | Medium | Medium | Medium | Large, modular systems |

---

### Change and Version Control

As a system evolves through testing and deployment, multiple versions exist simultaneously. **Change and version control** tools and processes manage this complexity.

**The version lifecycle:**

```
Alpha Version
(incomplete, internal testing)
        │
        ▼
Beta Version
(stable enough for end-user testing over extended period)
        │
        ▼
Production/Release Version
(formally distributed to users or made operational)
        │
        ▼
Maintenance Release
(bug fixes and small changes to existing features)
```

| Version Type | Definition |
|-------------|-----------|
| **Alpha version** | A test version that is incomplete but ready for rigorous integration or usability testing |
| **Beta version** | A test version that is stable enough to be tested by end users over an extended period |
| **Production version** (= Release version = Production release) | A system version formally distributed to users or made operational for long-term use |
| **Maintenance release** | A system update that provides bug fixes and small improvements to existing features |

## Summary

> Implementation and deployment are **complex processes** because they consist of many **interdependent activities**.

```
TESTING
├── Unit Testing          → individual methods/classes (Drivers & Stubs)
├── Integration Testing   → groups of components (interface issues)
├── System Testing        → entire system end-to-end
├── Performance/Stress    → response time + throughput under load
└── UAT                   → real users validate against requirements

DEPLOYMENT ACTIVITIES
├── Data Conversion       → migrate/load data from old system or manual records
├── User Training         → end users (hands-on) + operators (self-study)
│   └── Documentation     → system docs + user docs
└── Production Environment Config → infrastructure, servers, clients

MANAGING IMPLEMENTATION
├── Development Order     → IPO / Top-down / Bottom-up / Use-case driven
├── Deployment Strategy   → Direct (fast/risky) / Parallel (safe/costly) / Phased (balanced)
└── Version Control       → Alpha → Beta → Production → Maintenance
```
