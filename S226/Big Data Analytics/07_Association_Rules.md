## 1. Introduction

Association rule mining is an **unsupervised** and **descriptive** (not predictive) technique. It does not predict a target label — it discovers hidden, interesting relationships that already exist in the data, expressed as:

- **frequent itemsets** — groups of items that appear together often, and
- **rules** — statements of the form `{X} → {Y}`, meaning transactions containing X tend to also contain Y.

It is most commonly applied to mining transactions in databases (**market basket analysis**), but the same technique applies to clickstream analysis, spare-parts ordering, and recommender systems.

Typical questions it answers:
- Which products tend to be purchased together?
- Of customers similar to this person, what products do they tend to buy?
- Of customers who purchased this product, what else do they tend to view or purchase?

Classic example: `{Diapers} → {Beer}` — customers who buy diapers also tend to buy beer in the same transaction.

---

## 2. The Core Challenge: Combinatorial Explosion

**Why not just check every possible itemset?**

With *d* distinct items, the number of possible itemsets is **2^d** (including the empty set). A brute-force approach would treat every itemset in the lattice as a candidate, scan the entire transaction database, and count its support:

```
Complexity ≈ O(N × M × w)     where M = 2^d
```

(N = number of transactions, w = average transaction width). This is computationally infeasible for any realistic catalogue size — this is the problem the Apriori algorithm exists to solve, and **support** is the key concept that makes pruning possible.

---

## 3. Support and Frequent Itemsets

- **Support(X)**: given an item (or itemset) X, its support is the percentage of transactions that contain X.
- **Frequent itemset**: an itemset whose support is **≥** a chosen minimum support threshold (`min_support`).

Support is a simple statistic, but it is the *only* criterion used to decide whether an itemset survives to the next stage of the algorithm — which is what makes the next property so powerful.

---

## 4. The Apriori Property (Downward Closure)

This is the theoretical foundation the entire algorithm rests on:

> **If an itemset is frequent, then every subset of that itemset must also be frequent.**

Example: if `support({bread, jam}) = 0.6`, then it is guaranteed that `support({bread}) ≥ 0.6` and `support({jam}) ≥ 0.6`.

**The corollary is what actually enables pruning**: if an itemset X is **infrequent**, then **every superset containing X is also guaranteed to be infrequent**. In other words, once an item or combination is found to be too rare, no larger itemset built on top of it needs to be tested at all — this is exactly how Apriori avoids the 2^d explosion described above.

---

## 5. The Apriori Algorithm

Apriori takes a **bottom-up, level-wise** approach:

1. Identify all frequent **1-itemsets** (L₁) by counting each item individually.
2. Join surviving 1-itemsets into candidate **2-itemsets** (C₂), count their support, keep the frequent ones (L₂).
3. Join L₂ into candidate 3-itemsets (C₃) — only joining itemsets that are already known to be frequent — count, filter, repeat.
4. Stop when no candidate itemset meets `min_support`, or a predefined maximum itemset length is reached.

### Pseudocode

```
Apriori(D, min_support, N):
    L1 ← {frequent 1-itemsets satisfying min_support}
    k ← 2
    while L(k-1) ≠ ∅ and k ≤ N:
        Ck ← candidate itemsets generated by joining L(k-1)
        for each transaction t in database D:
            increment the counts of candidates in Ck contained in t
        Lk ← {candidates in Ck that satisfy min_support}
        k ← k + 1
    return union of all Lk
```

### Worked Example (classic textbook example)

Items: `Bread, Coke, Milk, Beer, Diaper, Eggs`. Minimum support count = 3 (out of some number of transactions).

**Step 1 — count 1-itemsets:** Coke = 2, Eggs = 1 → both fall **below** the threshold of 3 and are discarded immediately. Only 4 items survive: `Bread, Milk, Beer, Diaper`.

**Step 2 — generate candidate 2-itemsets:** because Coke and Eggs were already pruned, **no pair involving them needs to be generated at all** — an immediate saving. Only C(4,2) = 6 pairs are tested from the 4 surviving items:

| Pair | Count | Frequent? |
|---|---|---|
| Bread, Milk | 3 | ✓ |
| Bread, Beer | 2 | ✗ |
| Bread, Diaper | 3 | ✓ |
| Milk, Beer | 2 | ✗ |
| Milk, Diaper | 3 | ✓ |
| Beer, Diaper | 3 | ✓ |

Four pairs survive.

**Step 3 — generate candidate 3-itemsets:** joining the surviving pairs (per the Apriori join step) produces exactly **one** valid 3-itemset candidate: `{Bread, Milk, Diaper}`.

**Total itemsets actually examined:** 6 (singles) + 6 (pairs, only from the 4 surviving items) + 1 (triple) = **13**, compared to an exhaustive search over the original 6 items, which would require C(6,1) + C(6,2) + C(6,3) = 6 + 15 + 20 = **41** itemsets. Pruning two rare items early saved more than two-thirds of the work — and the savings compound at every additional level because the search space grows combinatorially.

## 6. From Frequent Itemsets to Rules

Having a frequent itemset L does not by itself give a rule — L must be split into an **antecedent** and a **consequent**.

**Rule generation:** for every non-empty subset *f* ⊂ L, the candidate rule `f → (L − f)` is valid (as long as `L − f` is also non-empty).

For an itemset of size *k*, the number of candidate rules is **2^k − 2** (subtracting the two trivial cases `L → ∅` and `∅ → L`).

Example, `L = {A, B, C, D}` (k = 4 → 2⁴ − 2 = 14 candidate rules):

```
ABC → D    ABD → C    ACD → B    BCD → A
AB → CD    AC → BD    AD → BC    BC → AD    BD → AC    CD → AB
A → BCD    B → ACD    C → ABD    D → ABC
```

The next question is: **which of these candidate rules can we trust?** — this requires evaluation measures.

---

## 7. Evaluating Candidate Rules

Three measures are used together, each answering a different question, applied roughly in this order: confidence (reliability) → lift (is it real, or just because the consequent is common?) → leverage (does it affect enough transactions to matter?).

### 7.1 Confidence

```
confidence(X → Y) = support(X ∩ Y) / support(X)
```

This is the **conditional probability** P(Y | X): of the transactions that contain X, what fraction also contain Y.

**Worked example (from the slides):** if `support({bread, eggs, milk}) = 0.15` and `support({bread, eggs}) = 0.15`, then:

```
confidence({bread, eggs} → {milk}) = 0.15 / 0.15 = 1.0 (100%)
```

Every transaction containing bread and eggs also contains milk.

**Anti-monotone property (important for efficient rule generation):** Confidence in general is *not* monotone — `c(ABC → D)` can be larger or smaller than `c(AB → D)`, because these come from two different base itemsets and are not directly comparable. **However**, for rules generated from the **same base itemset** `L = {A, B, C, D}`, moving items from the antecedent to the consequent (i.e. shrinking the antecedent) can only **decrease or keep equal** the confidence, never increase it:

```
c(ABC → D)  ≥  c(AB → CD)  ≥  c(A → BCD)
```

This follows directly from the Apriori property: `support(ABC) ≤ support(AB) ≤ support(A)` (a larger itemset can never have higher support than any of its subsets), and confidence = `support(L) / support(antecedent)` with `support(L)` fixed — a smaller antecedent means a larger denominator, hence lower confidence.

**Practical consequence:** just as Apriori prunes the itemset lattice using support, the *rule* lattice can be pruned using this property: generate rules with a single-item consequent first; any rule failing `min_confidence` guarantees that all further rules derived from it (by moving more items to the consequent) will also fail — so they never need to be tested.

### 7.2 Lift

```
lift(X, Y) = support(X ∩ Y) / (support(X) × support(Y))
```

Confidence alone can be misleading: if Y is already very common overall, `confidence(X → Y)` will be high regardless of whether X is really related to Y. Lift corrects this by comparing the observed co-occurrence rate to what would be expected **if X and Y were statistically independent**.

- `lift = 1` → X and Y are statistically independent (no real relationship).
- `lift > 1` → X and Y occur together **more often** than random chance predicts → a genuine positive association; larger values mean a stronger relationship.
- `lift < 1` → X and Y occur together **less often** than chance predicts → a negative association (the items substitute for one another).

**Worked example (from the slides):** 1,000 transactions; `{milk, eggs}` appears in 300, `{milk}` in 500, `{eggs}` in 400.

```
support(milk, eggs) = 0.3, support(milk) = 0.5, support(eggs) = 0.4
lift(milk → eggs) = 0.3 / (0.5 × 0.4) = 0.3 / 0.2 = 1.5
```

Milk and eggs co-occur 1.5× more often than independence would predict — a real positive association.

#### Understanding lift via a contingency table

A concrete way to see what lift means: build a 2×2 count table for two items across all transactions.

Example (392 transactions; item A in 38, item B in 37, both in 31):

| | Has B | No B | Total |
|---|---|---|---|
| **Has A** | 31 | 7 | 38 |
| **No A** | 6 | 348 | 354 |
| **Total** | 37 | 355 | 392 |

If A and B were independent, the **expected** number of transactions containing both would be:

```
expected = support(A) × support(B) × N = (38/392) × (37/392) × 392 ≈ 3.6
```

The **observed** count is 31 — about 8.6× the expected count under independence:

```
lift = observed / expected = 31 / 3.6 ≈ 8.6
```

This is algebraically the same formula as above, but framed as "how much more than random chance", which is the most intuitive way to read the definition given in the lecture: *lift measures how many times more often X and Y occur together than expected if they were statistically independent.*

**Symmetry — why lift differs from confidence:** because the formula `support(X∩Y) / (support(X) × support(Y))` treats X and Y identically, **lift(A→B) = lift(B→A)** always. Confidence is *not* symmetric (`confidence(A→B) = 31/38 = 0.816` vs `confidence(B→A) = 31/37 = 0.838` in the example above) because it divides by a different denominator each direction. Lift does not ask "which direction leads to which" — it only asks whether two events co-occur more than chance would predict, a question with no inherent direction.

**Limitation:** because lift is a *ratio*, it can be inflated by very rare itemsets — a pair that co-occurs only 2 or 3 times can still produce an enormous lift if the expected count under independence is tiny (e.g. 0.1), even though the statistical reliability and business impact of such a rule is minimal. This motivates the next measure.

### 7.3 Leverage

```
leverage(X → Y) = support(X ∩ Y) − support(X) × support(Y)
```

Leverage uses the same "compare to independence" idea as lift, but as an **absolute difference** rather than a ratio, expressed in the same units as support (percentage of all transactions).

- `leverage = 0` → statistically independent.
- `leverage > 0` → positive association (the larger the value, the larger the *share of transactions* affected).

**Worked example (same milk/eggs numbers):**

```
leverage(milk → eggs) = 0.3 − (0.5 × 0.4) = 0.3 − 0.2 = 0.1
```

Confirms the same conclusion as lift (positive association), and additionally tells us the absolute gap is 10 percentage points of all transactions.

**Why both lift and leverage are needed — a contrasting example.** Suppose a rare pair C, D: C in 5/392 transactions, D in 4/392, both in 3.

```
support(C) = 0.0128, support(D) = 0.0102, support(C∩D) = 0.0077
expected under independence ≈ 0.0128 × 0.0102 × 392 ≈ 0.05
lift = 3 / 0.05 ≈ 59        (extremely high!)
leverage = 0.0077 − 0.00013 ≈ 0.0076   (well under 1 percentage point)
```

| | A → B (common) | C → D (rare) |
|---|---|---|
| lift | 8.6 | **59** (much higher) |
| leverage | **0.070** | 0.0076 (much lower) |

Looking at lift alone, C→D appears far more "interesting". But leverage reveals the practical picture: A→B affects **7% of all transactions** — a large enough footprint to justify a real business action — while C→D, despite its huge lift, affects under 1% of transactions and may simply be noise from a handful of rare co-occurrences.

> **Rule of thumb:** lift answers "how strong is this relationship (relatively)?"; leverage answers "how much does this relationship matter across the whole dataset (in absolute terms)?" A trustworthy rule should score well on both.

### 7.4 Combining Measures

In practice, these measures are used together in a workflow: first filter candidate rules by a minimum confidence, then, among the survivors, sort or further filter by lift or leverage. **None of these three measures capture novelty** — a statistically strong rule may already be well known to the business (e.g. "buying bread and butter together" is not a new insight). Judging whether a rule is genuinely novel and actionable requires human/domain judgement, not a numeric threshold alone.

## 8. Applications of Association Rules

- **Market basket analysis** — better merchandising, product placement, and promotion planning.
- **Recommender systems** — discovering related products or similar customers.
- **Clickstream analysis** — analysing web browsing and click behaviour.
- Many more domains beyond retail.

## 9. Worked Example: the Groceries Dataset (R / `arules`)

The lecture demonstrates the full pipeline in R using the `arules` package on the built-in `Groceries` dataset: 9,835 transactions, 169 items, density ≈ 2.6% (i.e. each transaction contains on average only ~2.6% of all possible items — a very sparse matrix, structurally identical to the one-hot-encoded basket used in the Python `mlxtend` version of this lab).

```r
library(arules)
library(arulesViz)
data(Groceries)

itemsets <- apriori(Groceries, parameter = list(minlen = 1, support = 0.02,
                                                 target = "frequent itemsets"))
# → 122 frequent itemsets found

rules <- apriori(Groceries, parameter = list(support = 0.001, confidence = 0.6,
                                              target = "rules"))
# → 2,918 rules found
```

Note that the support threshold for **rule generation** (0.001) is set much **lower** than the threshold used just to find frequent itemsets on its own (0.02). If both stages required high support, many rare-but-strong rules would never be found — this mirrors why the France/Germany analysis in this course's Python lab used different `min_support` values per country.

Filtering and visualisation examples from the slides:

```r
confidentRules <- rules[quality(rules)$confidence > 0.9]
plot(confidentRules, method = "matrix", measure = c("lift","confidence"),
     control = list(reorder = TRUE))

highLiftRules <- head(sort(rules, by = "lift"), 5)
plot(highLiftRules, method = "graph", control = list(type = "items"))
```

Top rule by lift:

```
{Instant food products, soda} => {hamburger meat}
support = 0.00122, confidence = 0.632, lift = 18.99
```

This rule has very low support (only ~0.12% of transactions) but an extremely high lift — an excellent example of a rare-but-genuinely-strong relationship. If `min_support` had been set too high in the itemset-mining stage, this itemset would never have survived to be tested as a rule at all.

## 10. Validation and Testing

Not every statistically-generated rule is meaningful. Three pitfalls to check for:

- **Uninteresting rules** — involve items that are essentially unrelated, or are based on very few transactions (unreliable due to small sample size).
- **Purely coincidental rules** — a subtle but important trap: *if 95% of customers buy X and 90% buy Y, then X and Y are guaranteed to co-occur in at least 85% of transactions even if there is absolutely no relationship between them* (by inclusion–exclusion: `P(X∩Y) ≥ P(X) + P(Y) − 1 = 0.95 + 0.90 − 1 = 0.85`). A confidence of 85% here would reflect nothing more than the fact that both items are individually very common — not a genuine relationship. This is exactly why lift (not confidence alone) must always be checked.
- **Subjective criteria** — a rule can be statistically valid yet fail to reveal any new, profitable, or actionable insight; novelty and business value ultimately require human judgement.

---

## 11. Diagnostics

- Confidence, lift, and leverage should always be interpreted **together with human/domain insight**, never mechanically.
- Choosing `min_support` correctly is a genuine trade-off: too high a threshold discards rare-but-valuable rules before they are even generated (see the "Instant food + soda → hamburger meat" example above); too low a threshold causes a combinatorial explosion of candidates and excessive computation.
- Apriori can be computationally expensive on large item spaces; various algorithmic improvements exist beyond the scope of this lecture to address this.

## 12. End-to-End Pipeline Summary

```
Raw transactions
   │  (one-hot encode: 1 row per invoice, 1 column per item, 0/1)
   ▼
Apriori: count 1-itemsets → prune by min_support → join into 2-itemsets → prune → join into 3-itemsets → ...
   (Apriori property guarantees: an itemset containing an already-pruned item need not be tested)
   ▼
Frequent itemsets
   │  (for each itemset L, generate every antecedent/consequent split: 2^k − 2 candidate rules)
   ▼
Candidate rules
   │  (filter by min_confidence — rule generation can itself be pruned using confidence's
   │   anti-monotone property)
   │  (among survivors, rank/verify using lift and leverage to separate genuine
   │   relationships from base-rate coincidences)
   ▼
Statistically trustworthy rules
   │  (cross-check against domain knowledge — discard rules that are obvious,
   │   not novel, or not actionable)
   ▼
Actionable business insight
```

## 13. Common Misconceptions

**"Support measures how related two items are."** No — `support(X) = P(X)` is simply the raw frequency (or joint frequency, for a multi-item itemset) of X appearing, computed with **no reference to any other item**. It is *confidence* — computed only after frequent itemsets already exist — that measures a conditional relationship: `confidence(A→B) = P(B|A) = support({A,B}) / support({A})`.

**"If an itemset falls below `min_support`, it means the items are unrelated."** Not necessarily. The threshold exists for two reasons: (1) statistically, very rare co-occurrences are unreliable and, from a business perspective, too small to act on; (2) algorithmically, the Apriori property *guarantees* that any superset of an infrequent itemset will also be infrequent, so discarding it is mathematically safe, not a guess. However, Apriori prunes by **frequency**, not by **strength of association** — these are independent. A genuinely very strong relationship (high lift) between two rare items can be discarded purely because `min_support` was set too high, before it is ever examined (see the "Instant food + soda → hamburger meat" example, support = 0.0012, lift = 18.99 — it would have been silently discarded had `min_support` been set to, say, 0.01 instead of 0.001). Choosing `min_support` is therefore a deliberate computational trade-off, not a statement about which items are truly related.

**"A high confidence value proves a strong relationship."** Not on its own — see Section 10: two very common items are *guaranteed* by basic probability to have high confidence even with zero real relationship between them. Confidence must always be checked against lift.

**"Lift and confidence measure the same thing."** No — confidence is *directional* (`confidence(A→B) ≠ confidence(B→A)` in general) and is sensitive to how common the consequent is on its own. Lift is *symmetric* (`lift(A→B) = lift(B→A)`) and specifically corrects for the consequent's baseline frequency, answering "does A actually change the likelihood of B, beyond B's own base rate?"
